# 개발 로드맵

## 설계 원칙

> **구조를 흔들지 않는 것이 핵심이다.**
>
> 각 Phase는 이전 단계의 인터페이스를 변경하지 않고,
> 기능을 추가하거나 구현체를 교체하는 방식으로 확장한다.

## Phase 1: PoC 구현

### 목표

단계 분리 + 상태 관리 + 권한 검색이 실제로 동작하는 최소 시스템.

### 구현 항목

**인프라**
- [ ] Docker Compose 구성 (PostgreSQL + OpenSearch + App)
- [ ] DB 마이그레이션 스크립트 (5개 테이블)
- [ ] OpenSearch 인덱스 생성 (nori 분석기 포함)

**nas-scan-worker**
- [ ] 공식 반입 폴더 재귀 스캔 (1분 주기)
- [ ] 파일 안정화 판단 (mtime + size 비교)
- [ ] sha256 해시 계산 및 중복 감지
- [ ] raw_document 등록 (권한 메타 자동 추출)
- [ ] raw_document_scan_state 관리

**document-parse-worker**
- [ ] parse_status = PENDING 문서 배치 조회
- [ ] kordoc 호출 (PDF / DOCX / HWP / HWPX / TXT)
- [ ] markdown_text + blocks_json 저장
- [ ] parse_status 갱신 (DONE / FAILED)

**document-chunk-worker**
- [ ] chunk_status = PENDING 문서 배치 조회
- [ ] 제목 기준 청크 분리
- [ ] 1000~1500자 단위 추가 분리 + overlap
- [ ] document_chunk 저장 (권한 메타 포함)
- [ ] chunk_status 갱신

**document-index-worker**
- [ ] index_status = PENDING 청크 배치 조회
- [ ] OpenSearch Bulk 색인
- [ ] document_index_status 저장
- [ ] index_status 갱신

**chat-api**
- [ ] 사용자 인증 (Bearer Token)
- [ ] 권한 조건 구성
- [ ] OpenSearch 권한 필터 검색
- [ ] LLM 호출 (컨텍스트 구성)
- [ ] 출처 포함 응답 반환

**admin-api**
- [ ] 반입 문서 목록 조회 (상태별 필터)
- [ ] 실패 문서 목록 조회
- [ ] 전체 현황 요약
- [ ] 재처리 트리거
- [ ] 검색 제외 처리

**관리자 화면 (최소)**
- [ ] 문서 목록 테이블
- [ ] 상태 요약 카드
- [ ] 재처리 버튼
- [ ] 검색 제외 버튼

### PoC 완료 기준

- [ ] PDF 문서 반입 → 검색 → LLM 응답 전체 흐름 동작
- [ ] PUBLIC / DEPT / PRIVATE 권한 분리 동작 확인
- [ ] 실패 문서 재처리 동작 확인
- [ ] 관리자 현황 조회 동작 확인

### 구현 항목

**관리자 기능 강화**
- [ ] 중복 문서 목록 조회

**보안**

**확장 검색**
- [ ] Dense Vector 검색 (임베딩 모델 통합)

**인프라 확장**
- [ ] 워커 프로세스 분리 (독립 배포)
- [ ] 메시지 큐 도입 (Kafka 또는 RabbitMQ)

- [ ] DB 읽기 전용 복제본 (조회 분리)

**권한 강화**

- [ ] 문서별 개별 ACL
- [ ] 그룹 기반 권한

**OCR**
- [ ] 이미지 파일 OCR (Tesseract 또는 사내 OCR 엔진)
- [ ] 스캔 PDF OCR

**파서 관리**
- [ ] 파서 버전별 재파싱 일괄 처리

## 확장 시 변경 금지 원칙

각 Phase 확장 시 아래 인터페이스는 변경하지 않는다.

| 항목 | 내용 |
|------|------|
| DB 테이블 기본 구조 | 컬럼 추가는 가능, 삭제/변경은 마이그레이션 필수 |
| 상태값 규칙 | PENDING / DONE / FAILED 체계 유지 |
| 권한 필터 선행 원칙 | 어떤 Phase에서도 검색 전 권한 필터 적용 |
| kordoc 호출 위치 | Parse Worker 내부에서만 |
| document_parse_result 인터페이스 | markdown_text + blocks_json 구조 유지 |

## 우선순위 판단 기준

```
1. 운영 가시성 (상태 추적, 실패 감지)
2. 데이터 정합성 (권한, 중복, 이력)
3. 검색 품질
4. 기능 확장
5. 성능 최적화
```

성능 최적화보다 **정합성과 가시성**을 먼저 확보한다.
기능 확장보다 **안정적인 기반 구조** 유지를 우선한다.
